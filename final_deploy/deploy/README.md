# Лабораторный стенд ГИС (ПАСОИБ)

Стенд на **containerlab** (контейнеры, без виртуальных машин).

- **Домен:** `otlichnik.lab` (мастер-зона на FreeIPA, во внутренней сети)
- **DNS:** узел `dns` в ДМЗ — единый резолвер стенда
- **Технология МЭ:** Linux + `nftables`
- **Адресация:** статическая

## Развёртывание

```sh
sh scripts/deploy.sh          # деплой + первичная настройка (готовые образы не пересобираются)
```

`deploy.sh` собирает **только отсутствующие** образы, разворачивает стенд, ждёт
готовности FreeIPA, создаёт пользователей в IPA и готовит бандл VPN-клиента.
Повторный запуск не пересобирает образы — это быстрый способ переподнять стенд.

Флаги:

| Флаг               | Что делает                                                    |
|--------------------|---------------------------------------------------------------|
| `--rebuild`        | пересобрать образы перед развёртыванием (`--force`)           |
| `--skip-bootstrap` | не выполнять первичную настройку (IPA/VPN/АРМ)               |

Быстрый перезапуск (без сборки образов и без повторной настройки):
```sh
sh scripts/up.sh                    # собрать недостающие образы + deploy
sh scripts/up.sh --rebuild          # принудительно пересобрать образы
sh scripts/deploy.sh --skip-bootstrap
```

Сборку можно вызывать и напрямую:
```sh
sh scripts/build.sh                 # собрать только отсутствующие образы
sh scripts/build.sh --force         # пересобрать все
sh scripts/build.sh --force arm dns # пересобрать только выбранные образы
```
> `containerlab deploy` идемпотентен: уже развёрнутые узлы приводятся к
> состоянию топологии и не пересоздаются. Тома `ipa-data`/`vpn-data`
> переиспользуются, поэтому FreeIPA и PKI не ставятся заново.

Остановка:
```sh
sh scripts/down.sh
```

**Полностью с нуля** (переустановить FreeIPA и PKI):
```sh
sudo containerlab destroy -t topology.clab.yml --cleanup
docker volume rm ipa-data vpn-data
sh scripts/deploy.sh
```
> Тома `ipa-data`/`vpn-data` по умолчанию НЕ удаляются — FreeIPA и PKI
> переиспользуются между запусками.

### Про `ext-sw` / `dmz-sw` / `lan-sw`

Это **коммутаторы сегментов**. Бридж создаётся **внутри неймспейса** узла-держателя
(синтаксис `имя|узел`, например `dmz-br|dmz-sw`), поэтому:

- у самого узла-держателя **нет data-портов** — порты есть у бриджа внутри него;
- на хосте **нет хостовых бриджей и висящих правил iptables** — всё живёт в
  неймспейсах и создаётся/удаляется командами `containerlab deploy/destroy`.

### Про mgmt-сеть

Служебная сеть (`172.20.20.0/24`) оставлена **только у графических узлов**
`arm` и `ext-host` — как канал удалённого доступа (noVNC). Все остальные узлы
имеют `network-mode: none` и живут **только в своём сегменте**; доступ к ним —
через `docker exec` (сеть для этого не нужна). Резолвинг имён задан явно через
`/etc/resolv.conf` в init/entrypoint.

## DNS и домен

- `dns` (ДМЗ) — резолвер: зона `otlichnik.lab` (+ обратные) форвардится на
  FreeIPA (`10.10.20.10`), остальное — на `ext-dns` через `fw1`.
- `ipa` (`10.10.20.10`) — FreeIPA: Kerberos, LDAP, CA, свой BIND (мастер-зона).

## Межсетевые экраны (кратко)

- `fw1`: `DMZ → WAN` разрешён (+ NAT); извне — только `web:80/443` и `vpn:1194/udp`.
- `fw2`: `LAN → ДМЗ` разрешён; `ДМЗ → FreeIPA:53/389/636`; `vpn (10.10.10.14) → внутренняя`;
  прочее — `drop` с логированием.

## Сервисы и проверки

### Captive-портал (доступ АРМ в интернет — только после RADIUS)
`portal` (`10.10.20.2`) — шлюз АРМ. Схема работы:

1. АРМ открывает **любой внешний сайт** (например `http://example.com/news`).
   DNS стенда отдаёт на любое внешнее имя адрес `ext-web` (`198.51.100.80`),
   а `nftables` на портале перехватывает HTTP неавторизованного клиента
   (`prerouting ... tcp dport 80 redirect to :80`).
2. Портал запоминает исходный URL по IP клиента и показывает страницу входа.
3. Вход проверяется через `radclient` → RADIUS → LDAP FreeIPA. При
   `Access-Accept` IP клиента попадает в `nftables`-набор `authorized`
   (таймаут сессии — `SESSION_TIMEOUT`).
4. Портал отвечает `302` на **тот же исходный URL** — браузер открывает
   настоящий внешний сайт, а не заглушку «доступ разрешён».

АРМ (GUI): `http://172.20.20.100:6080/vnc.html` → Firefox сразу открывает
`http://example.com/` → страница портала → вход `testuser` / `UserPass123` →
открывается `example.com` (узел `ext-web`).

`ext-web` отдаёт одну и ту же страницу на любой `Host` и любой путь, поэтому
после входа открывается именно тот URL, который ввёл пользователь (адрес и
путь видны на самой странице).

Выход из сессии (чтобы повторить демонстрацию): `http://10.10.20.2/logout`.

> `portal.py`, `nftables.conf` и конфиг `ext-web` подключены в контейнеры
> bind-mount'ом — их правки применяются после перезапуска узлов. Изменения в
> `images/arm/entrypoint.sh` требуют пересборки: `sh scripts/build.sh --force arm`.

> Перехватывается HTTP. Имитация интернета в стенде — HTTP-only (`ext-web`
> слушает только порт 80), поэтому для HTTPS-сайтов captive-портал не
> срабатывает: для них нужен MITM-прокси с доверенным в браузере CA.

### АРМ в домене FreeIPA

`deploy.sh` вводит АРМ в домен (`scripts/arm-join.sh`): в зону добавляются записи
`arm.otlichnik.lab`/PTR, выполняется `ipa-client-install`, запускается `sssd`.

```sh
sh scripts/arm-join.sh
docker exec clab-gis-arm id testuser          # разрешается через SSSD из домена
docker exec clab-gis-ipa ipa host-find
```

### VPN для удалённого пользователя (LDAP)
Внешний пользователь (GUI): `http://172.20.20.101:6080/vnc.html` → xterm →
`vpn-up` → OpenVPN поднимается (учётка `testuser`/`UserPass123`) → доступ во
**внутреннюю** сеть (например `https://10.10.20.10/` — FreeIPA UI).

### IDS (Suricata)
`ids` — пассивный сенсор на ДМЗ; трафик с портов ДМЗ зеркалируется на него
через `tc mirred` (SPAN). Алерты: `docker exec clab-gis-ids cat /var/log/suricata/fast.log`.

### RADIUS
`radtest`/`radclient` к `10.10.10.15` (секрет `testing123`), аутентификация по LDAP.

### Логи (локальные)
`sh scripts/logs.sh <узел> [строк]`. Источники: firewall — `nft log group` + `ulogd`
→ `/var/log/nft.log` на МЭ; IDS — `fast.log`; VPN — `/var/log/ovpn-auth.log`;
IPA — `journalctl`; остальное — `docker logs`.

## Структура проекта

```
topology.clab.yml          топология containerlab
images/                    образы узлов (linux, dns, ipa, postgres, freeradius,
                           web, ftp, eml, vpn, ids, portal, arm)
configs/                   конфиги: fw1, fw2, dns, ext-dns, host, radius, web,
                           ext-web, ids, portal, dmz-sw
scripts/
  deploy.sh                деплой + первичная настройка (--rebuild, --skip-bootstrap)
  build.sh                 сборка образов (пропускает уже собранные; --force)
  up.sh / down.sh          (пере)запуск / остановка
  ipa-bootstrap.sh         пользователи в IPA (radius, testuser)
  vpn-client.sh            VPN-клиент (CLI) / подготовка бандла (--bundle-only)
  logs.sh                  просмотр локальных логов узла
```
